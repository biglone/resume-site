## 06. 源码/项目深读

## 项目定位
Whistle（鸣笛监控系统 V3）是一套面向道路现场声学事件监控的跨平台 C++ 系统，连接麦克风阵列、摄像头、声音识别、声源定位、车牌识别、证据生成与多种上报通道。V3 的核心目标是将短促事件控制在约 2 秒内、持续事件控制在约 5 秒内完成证据闭环，因此系统设计重点是实时管线的可预测性、设备异常的可诊断性和跨平台交付能力。

## 从源码抽出的架构
项目以 `wms_core` 为核心库，按实时数据边界拆为三段：
- **数据预处理**：`AudioReceiver`/`AudioUdpReceiver` 和摄像头适配层负责接收、解码、分帧、时间戳同步及缓存。音频以 1024 samples 为基础帧，并通过音频处理单元队列向后续算法提供稳定输入。
- **鸣笛识别**：识别服务从处理单元队列取数据，执行声音特征分析并输出鸣笛事件队列；定位模块再结合阵列数据计算声源区域。
- **鸣笛处理**：根据事件时间查询相邻视频帧，串联声源定位、车牌识别、证据任务、视频/图片/音频生成和 Reporter 上报。`EvidenceTaskExecutor` 会等待完整时间窗，再从音视频存储取数，避免证据截断。

## 关键技术难点
- **实时数据与业务解耦**：用阻塞队列、固定帧和 PTS/时间戳连接接收、识别与取证阶段，使算法耗时不会直接拖住设备接收线程。
- **多路车牌识别吞吐**：第三方识别组件存在单进程单路限制，项目通过多进程和共享内存消息队列扩展并发，并为超时和识别失败保留可观测状态。
- **设备协议兼容**：麦克风阵列启动时会探测协议版本并重试；针对偶发断连，定位 XMOS 固件中 UDP 反射忙等阻塞 uIP 事件循环的问题，推动从“重启规避”转为固件根因修复。
- **证据可靠性**：取证任务支持预录制时间、总时长、限流、阈值和重复任务判断；失败上报可进入持久化补传队列，避免网络抖动直接丢失现场记录。

## 工程化实现
核心使用 C++17、CMake 和 vcpkg 管理依赖，结合 Boost.Asio、FFmpeg、OpenCV、LevelDB、spdlog、GoogleTest、Qt6/QML、WebSocket 与 ActiveMQ 等组件。算法侧保留 OpenCV DNN/ONNX、YOLOv8/ByteTrack 等扩展入口；交付侧通过 Docker 和 GitLab CI 生成 Windows/Linux 构建产物，并用离线分析工具和测试程序复现现场数据。

## 模块边界与源码落点
- **应用编排**：`src/core/app.cpp` 负责系统配置、日志、状态存储和 WebSocket 服务启动；`wmsd` 是现场服务入口，`wms-cli` 与离线分析程序用于运维和回放验证。
- **设备接入**：`src/audio` 提供接收器、预处理和音频存储；`src/video` 与 `src/camera` 负责视频帧、解码、摄像头适配和时间戳；UDP 接收器通过 Boost.Asio 处理阵列协议探测和数据接收。
- **算法协作**：`src/recognition`、`src/localization`、`src/plate` 和 `src/object-detector` 分别承担声音识别、声源定位、车牌识别及目标检测扩展，业务层通过队列传递结构化结果。
- **输出闭环**：`src/evidence` 生成图片、视频、原始音频和违法记录，`src/reporter` 负责 HTTP/FTP 等上报以及失败补传；`src/storage` 为状态和补传任务提供持久化。

## 一个可复用的排障案例
麦克风阵列偶发离线时，表面现象是应用重连失败。通过日志、UDP 收发行为和固件事件循环对照，最终定位到 XMOS 固件中 UDP 反射逻辑的忙等阻塞，导致 uIP 事件循环无法持续处理网络事件。这个案例体现了我在跨进程、跨设备、跨语言边界上从现象复现、链路缩小到根因修复的排查方式，而不是只增加重启次数。
